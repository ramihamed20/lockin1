## 2. التعديلات المنفذة

التغييرات الجديدة محدودة بالأدلة: توحيد قفل إصدار جلسة الحساب وإبطالها، منع تكرار إعادة التحقق، تقليل تكلفة Analytics، فهرس الإيراد، إدارة لوحة الطالب كـ modal، حماية التأكيدات أثناء الطلب، skeletons الإدارة، الاحتفاظ الآمن بنتائج البحث، وتصحيح سباقي PWA وتهيئة PDF، واستعادة الجلسة عند commit، وautofill لكلمة المرور، وإغلاق اتصالات تعليقات IndexedDB عند مغادرة القارئ بعد تصريف الحفظ الجاري. حُفظت تعديلات الجولة السابقة والوظائف القديمة وعقود API.

## 3. تغييرات Backend

تقرأ إعادة التحقق حالة الحساب وcooldown داخل transaction مع select_for_update على المستخدم؛ عدم إصدار رمز جديد يمنع enqueue لبريد ثانٍ. إصدار الجلسة وإبطال الجلسات يشتركان في transaction وقفل المستخدم قبل التعامل مع الجلسات. دُمجت aggregates المتوافقة واستُبدلت JOINs المتضاعفة بـ Exists؛ النتائج وفترة البيانات كما كانت، دون cache جديد.

## 4. تغييرات Database وMigration


البيانات: 20,001 مستخدم، منهم 400 creator، و10,000 sheet و4,000 question و2,000 quiz و50,001 payment. أُجري ANALYZE وحُفظ SQL وEXPLAIN ANALYZE BUFFERS لكل استعلام. قورنت payloads كاملة مع نسخة البداية باستثناء generated_at؛ النتيجة مطابقة. الوسيط من ثلاث دورات بعد دورة تسخين، في cluster الاختبار المحلي ذي fsync المعطل؛ ليست هذه SLA أو قياس durability للإنتاج.

أُعيد القياس بحمل أوسع يضيف 20,000 Attempt و20,000 AttemptResult و30,000 LearningProgress و30,000 FocusSession، و10,000 إصدار sheet و2,000 إصدار quiz، مع تاريخ العمليات موزعًا على 730 يومًا ونافذة Analytics ثلاثين يومًا. البيانات اصطناعية وموجهة لاستعلامات Analytics؛ لا تمثل كل snapshots جلسات الإنتاج. بعد ANALYZE بقيت payloads مطابقة كاملة باستثناء generated_at: 46 إلى 26 استعلامًا، ووسيط 4186.23 إلى 149.09 ms. قياس الإيراد بفهرسه الجزئي: 5.593 إلى 0.252 ms. حُفظت الخطط قبل/بعد لكل استعلام في analytics-expanded-profile.json.

تُظهر الخطط أن تضاعف JOIN للـ creators كان الجزء الأكبر، نحو 3915 ms قبل الإصلاح. استُخدمت فهارس owner الموجودة مع Exists؛ فهرس الإيراد يحصر صفوف الفترة بدل تصفية بقية الصفوف الناجحة بعد جلبها. بقي Seq Scan لعد جميع المستخدمين، وهو متوقع للـ aggregate العام، ولتجميع progress وFocus بحسب الفترة. زمن كل من هذين التجميعين في العينة كان نحو 6–13 ms؛ لم يُضف فهرس آخر دون مقارنة تثبت فائدته. هذه حدود العينة، وليست ادعاءً بأن كل Seq Scan الأمثل لكل حجم مستقبلًا.

أُضيفت migration `payments.0007_payment_revenue_time_index`؛ CREATE INDEX CONCURRENTLY على PostgreSQL في migration غير atomic مع فصل حالة Django عن DDL، وعكس DROP INDEX CONCURRENTLY. لا backfill أو تعديل صفوف. الاختبار يبدأ من 0006 مع payment موجود، يرقّي إلى 0007 ويفحص indisvalid وpredicate وتطابق جميع الحقول، ثم يعكس ويرقّي ثانية. له fixtures مستقلة، بعدما كشف التشغيل الشامل تعارض إعادة تحميل fixtures العامة في setup.

## 5. concurrency والأمان


اجتازت مجموعة الحسابات المستهدفة 116 اختبارًا على PostgreSQL. اختُبر reset password وemail change وaccount deletion بمحاولتي استهلاك رمز متزامنتين: نجاح واحد واستهلاك واحد، دون deadlock في السيناريوهات المختبرة. اختُبر cancel deletion مقابل confirmation مع الحفاظ على الإلغاء وإبطال الرمز. signup بقي محميًا بقيد البريد في PostgreSQL، وتسجيل الدخول وإنشاء الجلسة والتحقق والحذف تحت الصلاحيات الحالية.

لم تتغير CSRF أو Secure/SameSite cookies أو throttles أو مدد الرموز أو حدود OTP. بقيت الاستجابات العامة لمنع enumeration وتدوير الجلسات ورفض replay وإبطال الرموز. القفل الجديد محدود بالسباقين المثبتين. هذا لا يثبت سقف burst موزعًا صارمًا أو غياب كل deadlock ممكن، ولم يُقَس توقيت enumeration عبر SMTP وشبكة إنتاج.

اجتازت استعادة الجلسة ثلاثة سيناريوهات بعشرة تكرارات متوازية لكل سيناريو بعد إصلاح commit، دون إخفاق. أربع حالات جديدة على 320px وiPad أفقي تختبر منع تكرار إنهاء الجلسة، autofill وأخطاء كلمة المرور، وخطوة حذف الحساب عبر البريد وإلغاء الطلب في RTL. تغيير البريد موجود في API ولا يوجد نموذج تعديل بريد موصول في Settings؛ logout-all موجود في API وأداة المستخدم الإدارية، دون زر مستقل في إعدادات الطالب. لم تُضف واجهات غير مطلوبة أو تُحذف هذه العقود.

## 7. الهاتف وiPad وإدارة التركيز


المصفوفة: 320×640، وAndroid 360×800، وiPhone 390×844، وiPad portrait 820×1180، وiPad landscape 1180×820، وdesktop 1440×900، باتجاه RTL، مع touch في أحجام الهاتف وiPad. تحققت من overflow وأخطاء JavaScript والتركيز وصور 320px وlandscape. هذه محاكاة متصفح وليست أجهزة فعلية. تحسنت أبعاد عناصر التحكم المشتركة إلى 44px، دون تغيير الصلاحيات أو منطق البيانات.

أُضيفت ست حالات خاصة بـ drawer على الأحجام نفسها: ارتفاع زر الإغلاق والحقل لا يقل عن 44px، عدم overflow داخل اللوحة، عرض كامل عند 320px، وإمكانية الإغلاق بعد التمرير. كشفت المراجعة أن container query لا ينطبق على portal، وأن system layer يعلو app layer؛ وُضعت قواعد أبعاد التحكم في system بنطاق الإدارة، وبقيت هندسة اللوحة في app. اجتازت الحالات الست الفحص بعد التصحيح.


كشف WebKit أن النقر على زر View لا يمنحه التركيز تلقائيًا؛ صار مسار الفتح يمنحه التركيز صراحة حتى تستطيع اللوحة إعادته بعد الإغلاق. اختُبر ذلك عبر تحميل مؤجل وTab وEscape، إضافة إلى حالة الخطأ.

## 8. Loading/Skeleton


امتد نظام Skeleton الموجود بثلاثة أشكال: admin-list وadmin-form وadmin-detail، باستخدام primitives نفسها. تفاصيل الطالب تحافظ على مكانها وتتيح الإغلاق خلال loading/error. أسماء التحميل تستخدم الترجمة الحالية. الأنواع الصريحة لقوائم الإدارة تمنع grid غير مشابه لقائمة النتائج. تفاصيل سجل مختلف لا تستخدم keepPreviousData حتى لا يظهر سجل قديم مكان الجديد. الخلفية أثناء refetch، والبيانات الفارغة، والخطأ، وoffline تحت حالات المكونات القائمة؛ error لا يُخفى من أجل إبقاء البيانات.

لم يُحسب CLS رقميًا لهذه الجولة؛ تقارب البنية والأبعاد فُحص بصريًا واختبارات loading، ولا يُقدّم كتحسن CLS مقاس. بقيت skeletons المتخصصة للـ Dashboard وReview والقارئ القائمة بدل استبدالها كلها بمكوّن عام.

## 11. المشاكل والحدود المتبقية

- WebKit المحلي لا يدعم decoder VP8 في حالتي الفيديو المذكورتين، ولا يتحقق من Ed25519؛ يبقى Offline مغلقًا عند تعذر التحقق، والدراسة أثناء الاتصال متاحة. لا تغيير للخوارزمية أو تخفيف للحماية.
- بعض النصوص الإدارية القديمة إنجليزية، وCRUD الهيكل غير الموصول لم يتحول إلى ميزة جديدة. المراجعة شملت السطح الفعلي في الراوتر، ولم تحذف compatibility.
- قياسات المتصفح على بيانات اصطناعية ومحاكاة أحجام؛ لا تشمل ذاكرة native وcanvases وService Worker كاملة أو جهاز iPad فعليًا، ولا تثبت غياب كل تسرب طويل الأمد.
- اختبارات الميزات غير المشحونة والمسارات opt-in تُذكر منفصلة عن النتائج الناجحة؛ لم تُستخدم بيانات إنتاج لتشغيلها.

## 12. مخاطر يجب مراقبتها عند النشر


- الفهرس المتزامن يحتاج وقتًا ومساحة وI/O بحسب حجم المدفوعات. راقب pg_stat_progress_create_index وindisvalid؛ الانقطاع قد يترك فهرسًا invalid يحتاج معالجة قبل إعادة migration.
- راقب انتظار قفل الحساب وزمن إنشاء وإبطال الجلسات. السباقات المحددة مختبرة؛ لا ادعاء بقدرة غير محدودة أو غياب كل deadlock.
- احتمال تكرار SMTP بعد قبول الرسالة وقبل تسجيل التسليم حد خارجي معروف من الجولة السابقة؛ منع تكرار HTTP resend لا يحقق exactly-once لدى مزود البريد.
- بيانات profiling اصطناعية وبعض المحتوى صغير. يلزم قياس PDF كبير وذاكرة native على iPad فعلي قبل ادعاء تحسين عام للقارئ.
- ترجمة الإدارة القديمة بالكامل والكتالوجات الضخمة جدًا وCRUD الهيكل غير الموصول ليست إعادة تصميم جديدة في هذه الجولة. لم تُحذف compatibility.
- فهرس الإيراد هو تغيير schema الوحيد. صور الإنتاج تُبنى مسبقًا وفق عقد النشر القائم؛ لم تُبنَ أو تُنشر على VPS هنا.
