# تقرير مراجعة الأداء

التاريخ: 2026-10-05. هذه المراجعة تبدأ من حالة المشروع بعد التنظيف السابق، بما فيها تعديلات المستخدم الموجودة. القياسات أدناه تخص تعديلات الأداء الحالية فقط.

## 1. المشاكل المثبتة وما تغيّر

### اتصالات IndexedDB تتزايد مع عدد السجلات

كانت `listOperations` وقراءة بيانات التنزيلات في `offlineDownloadStats` تجلب المفاتيح ثم تفتح اتصالًا ومعاملة منفصلة لكل سجل. أثبت القياس في Chromium أن قائمة من 500 سجل تحتاج 501 اتصالًا ومعاملة.

أضيفت `offlineDatabase.getMany` لقراءة المفاتيح المطلوبة في معاملة واحدة، واستخدمتها القائمتان. ترتيب القيم، والسجلات المفقودة، وفرز العمليات، وعزل المستخدمين بقيت كما هي. لا يوجد تغيير في مخطط IndexedDB أو اتصالات دائمة جديدة. فحص وجود محتوى التنزيلات في Cache/IndexedDB ما زال يعمل بالطريقة الأصلية.

### كود تخزين Focus يدخل ملف بدء التطبيق

كانت تهيئة Offline تستورد `focusSync`، الذي يستورد تخزين التعليقات ولقطات Workspace مباشرة. أظهر تحليل وحدات Rollup وجود أربع وحدات Workspace في ملف البداية، بمجموع 46,751 بايت قبل التصغير.

نُقلت استيرادات التخزين إلى داخل `flushDocument` مع الاستيراد المؤجل الموجود أصلًا للمزامنة. تسجيل معالج الطابور وفحص المستند المفتوح بقيا في موضعهما. اختفت وحدات Workspace الأربع من ملف البداية؛ تُحمّل عند تنفيذ مزامنة Focus أو فتح مسار يحتاجها. تبقى الملفات الجديدة ضمن precache حتى تعمل المزامنة دون اتصال.

### طلبات Streak متزامنة مكررة

أثبت تتبع الشبكة إرسال ثلاثة طلبات `/api/v1/progression/streak` عند بدء Dashboard: بطاقتا الشريط الجانبي ودرج الهاتف، وبيانات Dashboard.

تشارك الاستدعاءات المتزامنة الطلب الجاري ضمن كائن المستخدم الحالي باستخدام `WeakMap`. لا تُخزّن النتائج بعد اكتمال الطلب، ولا تُشارك بين كائنات مستخدمين أو جلسات مختلفة، حتى عند تطابق معرّف الحساب. تحديثات أحداث التقدم تتجاوز الدمج وترسل طلبًا جديدًا. الطلب اللاحق بعد انتهاء الطلب الأول يبقى مستقلًا للحفاظ على حداثة البيانات.

### N+1 عند قراءة النسخة المنشورة في كتالوج الطالب

في `/api/v1/catalog/materials` كانت جاهزية Active Study تقرأ `sheet.published_version` باستعلام إضافي لكل شيت. أثبت عدّ الاستعلامات داخل `source_version_for` وجود استعلام واحد لكل استدعاء.

أضيف `version__learning_object__published_version` إلى `select_related` في `_published_documents_by_subject`. أصبح ذلك الوصول بلا استعلام إضافي، وثبتت تكلفة حالة الاختبار عند 10 استعلامات. شُدّد اختبار ميزانية الاستعلامات لمنع رجوع النمو مع عدد الشيتات. لم تُغيّر فلاتر النشر أو الصلاحيات أو الإصدارات أو دالة الجاهزية.

قراءة 500 سجل أسرع بنحو 85% في هذا القياس المحلي. حجم JavaScript المحمّل عند بدء Dashboard انخفض نحو 22 KiB، وطلبات Streak انخفضت بنحو الثلث. هذه نتائج للمسارات المقاسة، وليست نسبة تسريع عامة للموقع.

منهج القياس:

- IndexedDB حقيقي في Chromium معزول، وبيانات اصطناعية متطابقة، وسبع قراءات لكل حالة؛ استُبعدت الأولى، وأُخذ وسيط الست الباقية. المقارنة القديمة والجديدة تمت في المتصفح نفسه، مع التحقق من تطابق القيم. الزمن يشمل قراءة القائمة وفرزها وفحص تطابقها؛ لا يشمل تجهيز البيانات.
- تحميل Dashboard: ثلاثة سياقات Chromium جديدة، محاكاة Pixel 5 مع إبطاء CPU أربع مرات، وواجهات API تجريبية، وService Worker محجوب لعزل تحميل التطبيق. عدد الطلبات وحجم JavaScript ثابتا النتيجة عبر العينات.
- زمن جاهزية Dashboard الوسيط المرصود انخفض من 2,410 إلى 2,186 ms، لكن العينة صغيرة والقياس يشمل انتظار `networkidle` وبيئة محلية. لم يُستخدم ذلك لإثبات تسريع عام للـ startup أو navigation.
- استعلامات Django قِيست عبر `CaptureQueriesContext` في SQLite، وهو وضع الاختبار الصريح المسموح في المشروع. أُعيد تشغيل الكتالوج على البيانات نفسها مع الاختيار القديم والجديد، وثبت تطابق JSON كاملًا مع 12→10 و17→10 استعلامات. لم تُقَس خطط PostgreSQL أو زمن قاعدة الإنتاج.

## 3. الحفاظ على السلوك والتحقق

بعد كل مجموعة تعديل شُغّلت اختبارات Node كاملة وESLint وtypecheck للواجهة والـ worker وبناء Vite. بعد تعديل Django شُغّلت أيضًا الاختبارات المرتبطة وRuff وmypy وDjango check.

النتيجة النهائية:

- **529 اختبار Node ناجحًا**، منها اختبارات جديدة للقراءة الجماعية، والترتيب، وعزل الحسابات، وصحة إحصاءات التنزيلات، ودمج الطلبات الجارية، والتحديث الإجباري، وإعادة المحاولة بعد الخطأ.
- **82 اختبار Chromium ناجحًا** في تسع مجموعات: auth، shell-navigation، sidebar-density، offline-pdf، offline-active-study، focus-workspace-persistence، focus-workspace-lifecycle، focus-workspace-stress، pwa-update.
- **28 اختبار Django ناجحًا** بعد تعديل الاستعلام: ميزانيات قوائم الإدارة والطالب، كتالوج Workspace، إصدارات الشيتات، Active Study عبر الإصدارات، وكتالوج الأسئلة. تشمل الاختبارات شكل الاستجابة، عزل الدفعات، منع الوصول، وحالة الملفات غير المتاحة.
- **12 اختبارًا لميزانيات استعلامات Django ناجحًا** في المراجعة الأولية، تغطي الكتالوج وFocus والبحث وhealth؛ أربعة منها أُعيد تشغيلها ضمن المجموعة السابقة.
- ESLint، TypeScript للواجهة والـ worker، Ruff، فحص تنسيق 651 ملفًا، mypy على 499 ملفًا، Django check، build، ميزانية bundle، و`git diff --check`: ناجحة.
- ملفات CSS المبنية احتفظت بالـ hashes نفسها، ومنها `index-Dht81dzH.css` و`CatalogFocusWorkspace-paPFTPyJ.css`. تعديلات الأداء لا تضيف عناصر DOM أو تغيّر CSS.
- precache انتقل من 73 ملفًا / 4392.92 KiB إلى 75 ملفًا / 4394.22 KiB بسبب فصل الملفات. هذه زيادة طفيفة في إجمالي ملفات التثبيت مقابل تحميل وتنفيذ أقل عند بدء الصفحة؛ إجمالي التطبيق لم ينخفض بالقدر نفسه الذي انخفض به ملف البداية.
- حُفظت فروق 49 ملفًا سابقًا دون تغيير؛ ملف `motivation.js` حافظ على تنظيفه السابق وأضيف إليه تحسين Streak فقط. أعيد `dist` إلى بناء الإنتاج العادي بعد بناء fixtures واختبارات المتصفح.

لم تُعَد مجموعة backend الكاملة أو جميع اختبارات المتصفح في هذه المراجعة؛ اختيرت المجموعات المرتبطة بالتغييرات. لم تُجرَ تغييرات schema أو migrations أو إعدادات نشر.

## إعادة القياسات محليًا

أدوات القياس وسجلاتها محفوظة في المجلد المحلي المتجاهَل `audit-artifacts`، ولا تُضاف إلى ملفات الإنتاج:

- `performance-idb.mjs` يقارن وحدة IndexedDB الأصلية المحفوظة بالحالية.
- `performance-bundle.mjs` يبني التطبيق ويجمع أحجام وحدات كل chunk دون تغيير محتواه.
- `performance-startup.mjs` يقيس ملفات وطلبات Dashboard عبر خادم المعاينة المحلي.
- `performance_query_capture.py` يلتقط أعداد الاستعلامات ويقارن الاستجابة القديمة والمحسّنة على بيانات الاختبار نفسها.

التقرير يوثق نتائج مختبر محلي؛ لم تُستخدم بيانات حسابات حقيقية أو قاعدة إنتاج، ولم يُنفّذ نشر.
